# Internal task observation before client exposure

This protocol is defined before reviewing real operations outcomes. No real-user task success or time saving has been measured by the implementation tests.

## Task set and acceptance

Ask operations for five to ten actual, anonymized Sales/Inventory tasks on a confirmed Odoo 19 installation. Capture the initial order/delivery/invoice state, invoicing policy, expected finished state and reviewer-approved source guidance **before** the session. Include a normal invoicing task, a partial delivery/backorder, an invoiced return/partial credit, a missing-condition task and an unsupported task. The development smoke questions are engineering checks; they do not replace this operations task set. Keep the seven frozen holdout questions sealed.

For this first internal review, require zero confidently wrong/unsupported actionable claims in the reviewed set, every shown citation ID/quote valid, no cross-version guidance, no cross-session data exposure, and useful clarification or escalation for unsupported tasks. A qualified Odoo reviewer must check semantics, screen transitions, assumptions and completeness, including any answer that passes model review. Any confidently wrong actionable claim blocks client exposure until corrected and rechecked. Safe abstentions count as unresolved tasks, not successful task completion.

Agree the maximum acceptable unresolved rate and a time-to-guidance target with operations before the timed trial; this is a missing product decision, not an engineering metric to invent. Current evidence gaps mean the pilot must remain an internal review tool until that decision and review are complete.

## Record each observation

Assign a task ID and anonymized participant label. Record the Odoo version, task family, initial conditions, the user's normal process/time on a comparable task, the pilot request IDs, total task time (including clarification and validation), correctness verified in the user's normal workflow, solved/partially solved/unresolved, escalation reason, reviewer support/completeness verdict and corrections. Do not ask the assistant to execute Odoo changes. Users remain responsible for normal authorization and execution in their own environment.

The UI records request-linked outcome, optional comment and task duration. The normal-process comparison, verified finished state and reviewer verdict belong in the observation log alongside the export; a positive outcome selection alone is not evidence of correct completion. Use a consistent timing method and avoid comparing a rehearsed pilot task with an unrelated difficult baseline task.

Review every unsupported/confident answer and every unresolved task. Report task completion and time compared with the normal process, clarification/escalation frequency, reviewer corrections, and user feedback. Decide whether a corpus gap needs a selected-page expansion, evidence assembly adjustment, or a better clarification; preserve versioned artifacts and report development results separately from frozen retrieval measurements.

The next observation is one operations user completing a real invoicing or partial-delivery task with the sources visible, while a reviewer checks the exact next actions. Odoo 19 is the confirmed scope; record the test installation as Odoo 19 when interpreting the outcome. Hosting/cohort selection and external publication remain pending.
